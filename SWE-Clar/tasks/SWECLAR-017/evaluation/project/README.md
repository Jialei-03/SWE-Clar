## Public HTTP and data contracts

JSON request bodies are UTF-8 objects with Content-Length1..16384 bytes. Invalid JSON, wrong types, missing required fields or out-of-range values return400 `{error:"invalid_request"}`. Invalid/missing Bearer session returns401 `{error:"unauthenticated"}`. An authenticated user with the wrong role for an otherwise accessible action gets403 `{error:"forbidden"}`. Unknown routes/methods, unknown records and offers belonging to unrelated users return404 `{error:"not_found"}`. A valid request conflicting with current business state/revision returns409 `{error:"conflict"}`. Extra request fields are ignored and cannot select the actor, owner, timestamps, computed labels, output records or revisions. Harmless additional response fields are allowed. IDs are opaque nonempty strings; no UUID/sequence spelling is required. Every successful mutation is durable, and failure preserves existing domain state.

`GET /health` ->200 `{ok:true}`. `POST /api/login {username,password}` ->200 `{token,user:{id,username,role}}`. Use an unpredictable session token derived from at least32 random bytes and keep sessions in memory. `POST /api/logout {}` invalidates only the presented session. Authenticated endpoints:

- `GET /api/catalog` ->`{user,now,listings:[listing]}`. All authenticated users see the same listings in fixture/insertion order. A listing summary has `{id,seller_id,title,price_cents,reference_price_cents,previous_price_cents,created_at,revision,status,labels}`. status is `active` or `sold`; labels is an array of strings. User objects never expose passwords or session tokens.
- `GET /api/listings/{id}` ->`{listing,questions:[question],offers:[offer]}`. Questions are public to authenticated users and remain in append order. The listing owner sees every offer for that listing; a buyer sees only their own offers; unrelated sellers see no offers. Offer content never leaks through caller owner/actor fields or another listing.
- `POST /api/listings/{id}/questions {text}` ->201 `{question}`. Buyers may ask questions on an active listing. Trim text at both ends to1..500 characters; preserve internal whitespace/case. The stored question is `{id,listing_id,author:{id,username},text}`. Derive the author from the session. No HTML execution or original personal content.
- `POST /api/listings/{id}/offers {amount_cents}` ->201 `{offer}`. A buyer may place an initial offer on an active listing; amount must be positive and at most the current asking price. Offer has `{id,listing_id,buyer_id,amount_cents,counter_amount_cents,status,version}`. New status=`pending`, counter_amount_cents=null, version0. Multiple distinct offers are permitted; independent submissions are not silently deduplicated.
- `PATCH /api/listings/{id}/price {price_cents,revision}` ->`{listing}`. Accessible to the listing owner. Validate cents and nonnegative integer revision (booleans excluded). Price history/version and conflict policies are clarified.
- `POST /api/offers/{id}/counter {amount_cents,version}` ->`{offer}`. Accessible to the listing seller, with offer visibility/role rules above. Validate cents and nonnegative integer offer version. Counteroffer lifecycle and amount policy are clarified.
- `POST /api/offers/{id}/accept {version}` ->`{agreement,listing,offer}`. Accessible to the offer's buyer. Validate nonnegative integer version; acceptance/replay/competing-offer policy is clarified.
- `GET /api/agreements` ->`{agreements:[agreement]}` in creation order, filtered to the current buyer or seller. Agreement has `{id,listing_id,offer_id,buyer_id,seller_id,amount_cents}`. It records local agreement only; no payment/notification/shipping side effect is claimed.

No mutation endpoint accepts user-supplied state snapshots. SQL schema and module organization are unrestricted. Stored questions/offers/agreements must come from actual authenticated operations, not static expected arrays or output intents.

## Public browser interface

Serve `/`, `/app.js`, `/style.css`. Export `MarketplaceClient` with `login(username,password)`, `logout()`, `refresh()`, `openListing(id)`, `ask(text)`, `offer(amountCents)`, `changePrice(priceCents)`, `counter(offerId,amountCents)`, `accept(offerId)`, `dispose()`. Observable fields: `catalog`, `detail`, `agreements`, `error`. Internal structures are unrestricted. Methods call real endpoints and render through exported `MarketplaceView(client,document)` with `dispose()`. The actual page boots through these classes.

DOM IDs: `login-form`, `username`, `password`, `login`, `logout`, `workspace`, `error`, `catalog`, `listing-detail`, `listing-title`, `listing-price`, `listing-status`, `listing-labels`, `questions`, `question-text`, `ask`, `offer-amount`, `place-offer`, `new-price`, `save-price`, `offers`, `agreements`. Listing selection controls have `data-listing-id`. Every displayed label has `data-label` containing its label code. Offer rows have `data-offer-id`; within a row the counter input uses `data-counter-amount`, counter button `data-counter`, accept button `data-accept`. Questions display literal author username/text; offer rows display actual amount, counter amount when present and status; agreements display listing ID and amount. Required controls may be hidden/disabled where inapplicable, with understandable errors on rejected actions. Styling, labels, harmless extra metadata and layout choices are free. Content is literal text, not injected HTML. Layout fits390x844 and1280x900 without horizontal page overflow.

UI money inputs represent integer cents; input labels make this clear. The UI sends the last-read listing/offer version with the relevant action, refreshes authoritative state after successful changes and conflicts, and preserves an understandable conflict error until a deliberate new action. Errors must not be displayed as success. Selection/login/logout controls remain usable while requests are pending; a reply initiated for a previous account or listing cannot replace current displayed data. Session tokens and private workspace data are not automatically restored from persistent browser storage. A fresh page starts logged out; logout/session invalidation clears current user data. Do not require a particular internal busy flag, exact prose or numeric text spelling beyond the stated amounts.
